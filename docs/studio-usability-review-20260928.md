# Studio 使用者视角调研 · 2026-09-28

## 结论

**当前 Studio 的功能链已经存在，但用户完成一件事的路径还不完整。** 首页、示例、设计、运行、回放和实验都有入口；问题集中在“先做什么、正在用什么、发生了什么、接下来怎么办”四个问题没有被连续回答。首页是最先暴露问题的地方，单独换一个漂亮首页不足以解决后续断点。

本次由用户提出体验问题并授权真实任务；Coding Agent 独立操作现有应用、运行两个普通 Agent 任务、保存浏览器证据，并针对部分问题检查源码。下面的改进方案是调研建议，尚未获得独立实施验收，也没有在本轮改动产品代码。

## 调研方法与边界

- 目标使用者：首次接触 ZhiXing、具有基本模型和 Android 知识的 Mobile Agent 研究者。没有把产品假设为面向所有人的无代码工具。
- 环境：当前本地工作区、实际运行中的 Studio 前后端、已配置的 `local-android` Android 模拟器；浏览器约 1280 × 720，标准字号，检查深浅主题。
- 路径：首页 → 正式示例 → Builder → Run → 真实任务 → 终态 → Replay → Inspector → History；另检查 Settings、Help、Benchmark Catalog/Composer 的验证和预览。
- 本次新建独立 Agent **UX Audit 2026-09-28**，使用正式推荐模板和默认模型标识 `gpt-4o`。没有修改已有用户 Agent。保留调研 Agent 与两个 Run 供复查；主题已恢复为调研前的深色，字号保持标准。
- 未启动 Benchmark Experiment，未修改 Android 设置值，未安装应用或发送消息。测试任务只涉及系统设置页面导航与观察。
- 这是一位评审者的探索式实测，不是多人可用性研究，不据此计算任务成功率、模型优劣或普遍 Android 兼容性。未做完整键盘、读屏、移动端、性能和安全审计。
- “实测”表示浏览器或本次 Run 证据；“源码”表示代码支持的判断；“建议”是尚未实施的设计。截图与可访问性文本见 证据目录 (not bundled in the core source)。部分早期文本是页面状态增量，截图保留完整可见画面。

## 最需要解释的五处断点

### 1. 首页问题包含真实状态错误

复现步骤：进入首页，观察“已就绪”，停留约 10 秒，不修改任何配置。运行准备变成“未知”，首次使用的运行步骤出现“需先完成运行环境配置”，同屏却仍写“3 个 Provider、1 个设备 Profile 已配置”。

源码链条：

- `studio/src/entities/runtime-readiness/api/runtimeReadiness.queries.ts:20`：进程查询 `staleTime: 10_000`。
- `studio/src/pages/studio-home/StudioHomePage.tsx:36`：`isStale`、`isFetching`、错误统一映射为 unknown。
- `studio/src/features/studio-onboarding/ui/StudioOnboardingCard.tsx:22`：任何非 ready 都显示“需先完成运行环境配置”。

缓存需要重验，不等于配置消失。这也是为什么用户会感觉系统“总是不准备好”。不能用永久绿色掩盖过期；可以保留“上次配置检查通过 · 待复查”，在真正发起运行时执行原有精确版本检查。

首页缓存过期后出现相互矛盾的提示 (image not bundled in the core source)

### 2. 首次运行缺少可理解的起点

当前顺序是“选模板 → 自动创建 revision → 打开完整画布 → 自己找 Run → 输入任务”。虽然这条路能走通，但用户必须先理解设计器，才接近自己的目标。

正式模板缺少“适合做什么、已配好什么、还需提供什么、首次建议输入什么、看到什么算完成”的说明。默认模型 `gpt-4o` 能在 `zhixing/studio/data/flow_templates/modular_baseline.json:80` 和 Reasoning 的 LLM 表单中找到，但运行准备页没有同等醒目的摘要。

建议先提供“运行这个示例”和“编辑这个 Agent”两个明确目的。首次推荐任务必须用目标设备状态验证，写清起始状态和成功观察；本次仅观察设置首页成功，不足以认证从任意屏幕打开设置的完整示例。保留画布的研究能力，但不让熟悉画布成为首次试跑的前提。

### 3. 运行监控拥有事件，不一定拥有用户需要的解释

本次选中第二次交互的推理 activation 后，“组件详情”的输入、输出均提示没有可展示的安全摘要。技术详情中完整模型响应与 Prompt 为 `not_captured`；可打开的安全 payload 主要是 graph kernel 开始/完成事件及 `keys/type` 结构描述。它不能解释为什么选择某个点击目标。

源码 `studio/src/features/run-inspector/model/runStoryPresenter.ts:455` 在没有摘要事实时退回“该步骤已完成”。因此，界面有完整步骤列表不代表这次运行的语义信息完整。

**目前不能从这次页面检查断言全部底层文件都没保存模型信息。** 后续需要沿组件输出 → 事件/轨迹 → Replay 映射 → Inspector 展示逐层定位采集或映射缺口。建议采集允许公开的结构化动作、观察引用、结果和简明决策说明；这不要求披露隐藏思维链，也不能把原始秘密直接放入 UI。

推理步骤的输入输出没有可展示摘要 (image not bundled in the core source)

### 4. 失败后的恢复比“显示失败”更重要

这次失败有明确预算终止事实，界面主要给英文错误；进入完整回放默认重置到最初，没有先回答“停在哪里、最后看到了什么”。点击“定位失败事实”能把游标移到终点，但观察到右侧过程仍停在早期交互位置。回放还有新的任务输入栏，不过未预填刚失败的任务，重试的连续性较弱。

建议终态先呈现：任务目标、成功/失败及其证据来源、停止原因、最后截图、最后几步动作，再提供“查看失败步骤”“修改配置后重试”“复制任务再运行”。英文技术错误和完整事件列表可以展开。对重复动作可以陈列事实，但不能凭重复就自动断言根因。

成功对照还显示另一种语义错位：Done 没有设备副作用本来是正常结果，页面却写“尚未确认设备副作用”（`runStoryPresenter.ts:438`）。需要区分“不适用”和“未知”。手机 Interaction 0、过程“交互 1”、另一个终态“交互 2”也缺少计数语义解释；这里记录的是呈现歧义，不认定运行时计数错误。

### 5. 历史与实验入口要求用户记内部身份

普通历史中，刚创建的 Agent 名称 `UX Audit` 搜索不到；`studio/src/pages/run-history/RunHistoryPage.tsx:26–27` 仅匹配 Run ID、Agent ID。搜索框已说明“当前页”，所以这里不声称全库搜索承诺被违背，但按名称找运行仍是明显缺口。`89% · complete` 等组合没有向使用者解释覆盖率和完整性是不同维度，容易误读。

Benchmark Catalog 实际有 External Photo Smoke、AndroidWorld（81 tasks）、AppAgent（45 tasks），不是空壳。但 Composer 的选项只有任务 ID（`ExperimentCreatePage.tsx:304`）；本次完成验证与预览后仍看不到所选任务的自然语言目标、初始化影响等决策信息。本轮没有创建 Experiment，因此不评价其 Monitor/Report/Export 的实际体验。

## 首页应该承担什么

建议把首页定位为“研究工作台的开始与继续”，按照现有真实状态组织，而不是继续堆产品口号或总数。

| 场景 | 首屏必须回答的问题 | 建议内容 |
| --- | --- | --- |
| 第一次来 | 我能先试什么？缺什么？点哪里？ | 一张经过验证的示例任务卡：目标、起始设备条件、预期结果、主要模型/设备选择、开始操作 |
| 尚未配齐 | 缺哪一项？如何补？ | 具体缺项及直达解决入口；不要把未知当作未配置 |
| 有任务执行中 | 它现在怎么样？怎样继续查看/停止？ | 当前任务名称、Agent、真实运行状态，继续查看入口；只提供现有协议支持的停止行为 |
| 已经运行过 | 上次做了什么？成功了吗？下一步是什么？ | 最近任务目标、Agent 名称、状态、时间；查看结果、重试、继续设计 |
| 进入研究评测 | 怎样验证一个 Agent？ | 独立 Benchmark 入口、具体任务与评估说明，保持 ordinary Run 和 Experiment 各自语义 |

建议的首屏顺序：**当前任务/首个示例 → 模型与设备准备 → 最近研究工作 → 示例与帮助**。首次指引从真实资源查询推导；不靠 localStorage 伪造“已完成运行”。首页当前仅通过 Replay 列表展示普通结果，因此缺少活动 Run 的直接工作台入口是源码层面的发现；本轮没有在任务运行途中导航回首页验证这一项。

## 建议实施顺序与验收

以下为独立后续变更建议，不是本轮已修复项，也不扩展运行内核或 Benchmark Worker cardinality。

### 第一批：修复误导，恢复用户信任

处理 U01、U06、U11、U16，并将主要错误转换成有依据的用户描述。

- 首页静置超过缓存时效，不提示“配置丢失”；实际缺项、网络失败、刷新中分别可辨识。
- 同一终态在标题、图、手机、Inspector 中一致；Done 无副作用显示“不需要设备动作”。
- 用 Agent 名称与任务摘要能找到本次记录；明确搜索范围，身份信息可复制。
- 无效账户/偏好控件不再诱导点击。以上可用无设备状态测试和浏览器回归验证。

### 第二批：打通第一次运行与失败重试

处理 U02、U03、U04、U05、U08、U09、U12、U13；首页与 Run/Replay 作为一条旅程设计。

- 用户不需要读源码、找 SecretRef 或学习节点依赖，就能确认模型、设备、任务和停止规则。
- 主动连接检测必须是明确命令；静态配置读取、编译和验证仍无设备/模型副作用。模型探测如会产生调用费用，应在操作处说明。
- 从已知设备起点验证一个推荐示例；分别保留真实成功与可控失败路径。
- 失败进入回放时，首先可见停止原因、最后观察与相关步骤；选择推理步骤能看到允许披露的语义输入/输出，缺失则明确原因。
- 从失败结果再次运行能保留任务上下文；若使用更新后的 revision，明确提示版本变化。
- 通过真实 Android 轨迹验收；测试数据和真实运行证据分别标识。

### 第三批：研究工作效率与统一表达

处理 U07、U10、U14、U15；完善任务选择、语言、层级和布局。

- Benchmark 创建前可读到具体任务及初始化影响；身份哈希放入复现详情。
- 常用模型参数和图的高级配置分层，标准屏幕上重要说明可读；再扩展小屏、键盘、读屏验证。
- 用户流程中不出现 Stage 编号、durable create、开发变更说明等无助决策的文字。
- 请首次使用者做“开始任务、确认结果、查失败、找到历史”四项观察测试，记录耗时、误点、求助与完成情况；不要把本次专家走查当作这些用户数据。

## 复查方式

在已配置环境中，从项目根目录执行：

```bash
conda activate unimobile
python run_studio.py
```

已有前后端正在运行时直接打开当前页面，不重复启动。然后：

1. 首页停留超过 10 秒，比较准备状态与首次引导的提示。
2. 在普通 Runs 搜索 `UX Audit`，对比未筛选时存在的调研记录。
3. 打开上方失败 Replay，观察默认落点；定位失败，再选择推理步骤查看组件详情与技术证据。
4. 打开成功对照 Run，查看终态的“当前执行”、LIVE 和 Done 文案。
5. 进入 Experiments，选 AndroidWorld 与一个任务，完成验证和预览；检查是否足以理解接下来要执行什么。复查此项不需要点击创建。

真实任务复跑会产生新的模型调用和设备导航。本报告已有结果可直接复查；再次运行结果可能受设备起始状态、模型和环境变化影响，不能保证复现同一动作序列。

## 工程复盘

此前一键启动解决了服务和配置装配成本，这次实测说明启动顺畅之后，仍存在前端状态映射、用户任务呈现和证据可读性问题。应该保留后端明确的 Graph、immutable revision、设备副作用、Run/Experiment 边界，在用户决策处提供语义摘要和连续导航。替代方案是整体重做首页或重写运行架构，前者无法解决证据断点，后者成本高且缺少本次调研支持。

本轮没有代码修复前后对比。已验证的是“实际旅程 → 两次 Run → 终态/回放检查 → 源码定位”的调查链。可复述的工程解释与追问见 面试复盘 (not bundled in the core source)。
